# Проміжне ревʼю критичних і високопріоритетних проблем

**Дата:** 2026-08-18  
**Статус:** підтверджено статичним аналізом; виправлення ще не реалізовані.  
**Обсяг:** критичні та високопріоритетні знахідки попереднього ревʼю, крім PBKDF2/signature path і
транзакційності створення розмови, які свідомо залишаються без змін.

## Висновок

Першим слід закрити єдину наскрізну проблему авторизації: зараз таблиця
`conversation_participants` визначає, що користувач бачить у списку розмов, але не обмежує читання,
запис або WebSocket-підписку. Після цього треба виправити міжкористувацьку дедуплікацію та stored XSS.

Рекомендований порядок нижче враховує і серйозність, і залежності. Кожна група є окремим,
самодостатнім PR.

## PR 1 — Єдина межа авторизації розмов

**Пріоритет:** P0 — робити першим.

### Підтверджені проблеми

- `GET /api/messages` у `src/routes/messages.ts:51` не використовує `requireSession` і не перевіряє
  участь користувача в розмові. Анонімний клієнт може перебирати `conversationId` і читати історію.
- `src/ws/hub.ts:97-118` приймає WebSocket без сесії, а `subscribe` довіряє переданим
  `conversationIds`. Це дозволяє анонімно отримувати realtime-події чужих розмов.
- `sessionOrQueryUserId` у `src/middleware/session.ts:49-70` приймає `?userId=` як доведену
  ідентичність. Через це список розмов іншого користувача доступний без сесії.
- `POST /api/messages` автентифікує відправника, але не перевіряє його участь у `conversationId`.

### Межа PR

- Прибрати fallback на `?userId=` і вимагати дійсну сесію для читання розмов та повідомлень.
- Додати спільну перевірку участі в розмові для HTTP read/write шляхів.
- Автентифікувати WebSocket під час upgrade через ту саму серверну сесію.
- Дозволяти підписку лише на розмови, учасником яких є власник сокета; перевіряти `Origin`.
- Не розкривати існування чужої розмови: повертати однакову відповідь для відсутньої та
  недоступної розмови.

### Критерій готовності

Анонімний запит, інший залогінений користувач і WebSocket із неавторизованою підпискою не можуть
читати, створювати чи отримувати події чужої розмови. Авторизований учасник зберігає поточну
поведінку.

## PR 2 — Ізоляція ідемпотентності між користувачами

**Пріоритет:** P0 — після або паралельно з PR 1.

### Підтверджена проблема

`client_id` глобально унікальний у `docker/db/mysql.sql:31`, а пошук дубліката в
`src/services/messages.ts:53-63` не обмежений відправником або розмовою. Оскільки `clientId`
контролює клієнт, колізія повертає йому metadata і Mongo body чужого повідомлення та мовчки скасовує
його власне надсилання.

### Межа PR

- Замінити глобальний unique index на `(sender_id, client_id)`; за потреби включити
  `conversation_id`, якщо retry має бути локальним до розмови.
- Застосувати той самий scope у lookup дубліката.
- Відхиляти конфлікт, якщо повторний запит не збігається з первинними `conversationId` і body,
  замість повернення стороннього або семантично іншого повідомлення.
- Передбачити міграцію наявного індексу, а не лише зміну bootstrap-схеми.

### Критерій готовності

Однаковий `clientId` різних користувачів не спричиняє витоку чи втрати повідомлення; retry того
самого запиту того самого відправника повертає початковий результат без нового broadcast.

## PR 3 — Контекстне кодування назв у браузері

**Пріоритет:** P0.

### Підтверджена проблема

`web/app.js:161-162` вставляє `c.title` через `innerHTML`. Регулярний вираз у
`src/validation/messageInput.ts:28-31` не видаляє незакритий тег на кшталт
`<img src=x onerror=...`, тому серверна blacklist-санітизація не є межею безпеки.

### Межа PR

- Побудувати DOM-вузли та встановлювати користувацьку назву через `textContent`.
- Залишити серверну нормалізацію як перевірку формату, але не вважати її XSS-захистом.
- Перевірити інші `innerHTML`-синки, куди може потрапити збережений або відбитий ввід.

### Критерій готовності

Назви з HTML, незакритими тегами та event-handler атрибутами відображаються лише як текст і не
створюють DOM-елементів.

## PR 4 — Масштабований список розмов

**Пріоритет:** P1.

### Підтверджена проблема

Derived table у `src/routes/conversations.ts:42-46` виконує `GROUP BY` по всій таблиці `messages`
для кожного запиту, а фільтр користувача застосовується лише після агрегації. Вартість запиту росте
від загальної кількості повідомлень у системі.

### Межа PR

- Обмежити агрегацію conversation IDs поточного користувача або замінити її корельованим планом,
  підтвердженим через `EXPLAIN ANALYZE`.
- Зберегти один SQL round-trip і поточний response contract.
- Додати regression/performance перевірку з великою кількістю чужих повідомлень.

### Критерій готовності

План запиту не агрегує всі повідомлення системи для користувача з малою кількістю розмов; час і
examined rows залежать переважно від розмов цього користувача.

## Залежності й порядок

1. PR 1 — закриває найбільшу поверхню несанкціонованого доступу.
2. PR 2 і PR 3 — незалежні P0-виправлення, можуть виконуватися паралельно після узгодження контрактів.
3. PR 4 — масштабування read path.

PR 1 і PR 2 повинні бути узгоджені щодо відповіді на чужий або конфліктний `clientId`, щоб
авторизація не перетворилася на oracle існування повідомлення.

## Свідомо поза обсягом

- **PBKDF2/signature path:** залишається без змін за рішенням користувача.
- **Транзакційність створення розмови:** залишається без змін за рішенням користувача.
- Середні та низькі знахідки попереднього аудиту не включені до цього плану.
- Цей документ не стверджує, що проблеми вже виправлені: це проміжне статичне ревʼю і план
  розбиття, а не fix note.

## Alternatives considered

- **Один великий security/architecture PR.** Відхилено: змішує schema migration, HTTP/WS contracts,
  frontend rendering і SQL performance; такий PR складно перевірити й безпечно відкотити.
- **Окремий PR на кожну проблему авторизації.** Відхилено: точкові перевірки залишили б різні
  правила доступу між HTTP та WebSocket і створили б проміжні обхідні шляхи.
- **Спочатку додати лише middleware до `GET /api/messages`.** Відхилено: автентифікація без
  membership authorization не закриває IDOR.
- **Посилити regex-санітизацію для XSS.** Відхилено: blacklist не є надійною межею; контекстне
  кодування через `textContent` усуває клас атак у цьому sink.

## Dead ends

Під час цього проміжного ревʼю реалізаційні підходи не випробовувалися і не відкидалися на основі
runtime-результатів. Наведені ризики підтверджені читанням коду; команди відтворення та red/green
числа мають зʼявитися у відповідних spec/fix notes під час реалізації кожного PR.
