# Аудит архітектури Relay

**Дата:** 2026-08-18
**Обсяг:** статичний аналіз усього репозиторію — `src/`, `web/`, `docker/`, схема MySQL, конфігурація compose/Envoy.
**Статус:** аналіз без внесення змін у код. Жоден із описаних дефектів ще не виправлений.

## Метод і його межі

Це аудит **читанням коду**, а не навантажувальним тестуванням. Єдина цифра, яку я реально виміряв —
вартість `pbkdf2Sync` (див. C1); решта оцінок — це механізми, виведені з коду, і кожну з них слід
підтвердити вимірюванням перед тим, як заявляти про виправлення. Репозиторій вимагає підходу
«спочатку докази» (`.cursor/skills/relay-load-bug-triage`), тому до кожного пункту я додав команду
відтворення. Позначка **(не перевірено)** означає, що механізм виведений з коду, але ще не
відтворений на запущеному стеку.

Оцінка серйозності: **Критично** — втрата чи пошкодження даних або падіння процесу;
**Високо** — деградація, помітна користувачам, під реальним навантаженням;
**Середньо** — накопичувальний ризик або дірка в безпеці за межами демо-сценарію;
**Низько** — якість коду й підтримуваність.

## 1. Concurrency & Race Conditions

### Сценарій: 50 користувачів надсилають повідомлення одночасно

Це прямо запитане в завданні, тому спершу — цілісна картина, а далі розбір кожного механізму.

Envoy розподіляє запити круговим методом, але за замовчуванням стек піднімається з **одним**
інстансом `api`, тож усі 50 запитів потрапляють в один процес Node. Далі, по порядку:

1. **Черга на CPU.** Кожен `POST /api/messages` синхронно рахує `pbkdf2Sync` (C1). Виміряно 17 мс
   на цій машині; у контейнері на повільнішому CPU — помітно більше. Оскільки виклик синхронний, він
   не йде в пул потоків libuv, а тримає єдиний потік. 50 запитів = **щонайменше ~0.85 с суцільно
   заблокованого event loop**, і це до будь-якої роботи з БД. Останній у черзі чекає весь цей час.
2. **Стоїть увесь застосунок, а не лише надсилання.** Поки event loop заблокований, не обробляються
   ні `GET /api/conversations`, ні кадри WebSocket, ні health-перевірки. Симптом виглядає як «усе
   гальмує», а не «надсилання гальмує» — це ключ до діагностики.
3. **Пул БД стає другим вузьким місцем.** `mysql.createPool` без параметрів дає `connectionLimit: 10`
   і `queueLimit: 0`, тобто **необмежену** чергу очікування (C5). 50 паралельних вставок шикуються
   по 10; черга не має ні межі, ні таймауту й росте в памʼяті.
4. **Користувачі починають повторювати.** Відповідь іде секундами, людина тисне «Надіслати» ще раз.
   Дедуплікації за `client_id` немає (C3), тож кожне повторення створює **нове** повідомлення.
   Навантаження саме себе підсилює: повільно → повтори → більше pbkdf2 → ще повільніше.
5. **Одна погана відповідь БД вбиває процес.** Помилки не обробляються ніде (C4): у Node 22
   незахоплений rejection завершує процес. `restart: on-failure` тихо його підіймає, і при цьому
   **рвуться всі WebSocket-зʼєднання** цього інстанса, а клієнт не перепідключається (R3).
6. **Після падіння лишаються биті повідомлення.** Якщо процес помер між вставкою в MySQL і вставкою
   в Mongo (C2), рядок є, тіла немає. `src/routes/messages.js` маскує це через `?? ''`, і
   повідомлення назавжди рендериться порожньою бульбашкою.

Тобто на 50 одночасних надсиланнях ламаються не «якісь мілісекунди», а чотири різні речі одразу:
затримки, дублікати, розірваний realtime і мовчазна втрата тіл повідомлень.

**Як відтворити:**

```bash
# у першому терміналі — вимірюємо звичайне читання
while true; do curl -s -o /dev/null -w '%{time_total}\n' 'localhost:3000/api/conversations?userId=1'; done

# у другому — 50 паралельних надсилань
seq 1 50 | xargs -P 50 -I{} curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST localhost:3000/api/messages -H 'content-type: application/json' \
  -d '{"conversationId":1,"senderId":1,"body":"concurrent {}"}'
```

Якщо час простого `GET` підскакує з одиниць мілісекунд до секунд — заблокований event loop, а не
повільна БД.

### C1. Синхронне підписання блокує event loop — **Критично**

```ts
const signature = crypto
  .pbkdf2Sync(body, 'relay-signing', 200000, 32, 'sha256')
  .toString('hex');
```

`src/services/messages.ts:15-17`. Виміряно **17.1 мс** на виклик (Node v22.22, Apple Silicon,
середнє з 5 запусків). Тріаж-скіл репозиторію називає ~100 мс — там, вочевидь, повільніше залізо;
цифру треба переміряти всередині контейнера, бо саме вона визначає масштаб проблеми.

Незалежно від точного числа, механізм той самий: `pbkdf2Sync` — синхронний, не використовує пул
потоків, і монополізує єдиний потік Node на весь час обчислення.

Головне питання — не «як зробити це швидше», а **чи потрібне це поле взагалі**. `signature`
записується в Mongo і **ніде не читається**: ні в роутах, ні у фронтенді. Це підпис на секреті,
захардкоділеному в коді, який нічого не перевіряє. Найчесніше рішення — прибрати його і зафіксувати
це рішення в `docs/`. Якщо підпис усе ж потрібен, то це або асинхронний `crypto.pbkdf2`, або взагалі
винесення за межі шляху запиту; для підпису HMAC доречніший за KDF.

### C2. Подвійний запис без атомарності — **Критично**

`createMessage` вставляє рядок у MySQL, потім документ у Mongo (`src/services/messages.ts:19-33`).
Транзакції немає, компенсації немає, повторів немає. Будь-який збій між двома записами — падіння
процесу, розрив мережі, таймаут Mongo — лишає повідомлення без тіла назавжди.

Проблема посилюється тим, що наслідок **приховано**: `src/routes/messages.js` читає
`bodyById.get(r.id) ?? ''`, тож пошкоджений запис виглядає як порожнє повідомлення, а не як помилка.
Розбіжність не потрапляє ні в логи, ні в метрики.

**Перевірка розбіжності:**

```bash
docker compose exec mysql mysql -uroot -proot relay -N -e "SELECT COUNT(*) FROM messages"
docker compose exec mongo mongosh relay --quiet --eval 'db.message_bodies.countDocuments()'
```

Варіанти рішення, від найпростішого: писати тіло **першим** (осиротіле тіло нешкідливе, бо його
ніхто не прочитає без рядка в MySQL) — але це конфліктує з тим, що `_id` береться з autoincrement
MySQL; або аутбокс із фоновою доставкою; або перенести тіло в MySQL і прибрати подвійний запис як
такий. Мінімум — перевести `?? ''` на явну позначку пошкодженого запису й лічильник.

### C3. Надсилання не ідемпотентні — **Високо**

Фронтенд генерує `crypto.randomUUID()` на кожне надсилання, колонка `client_id VARCHAR(64)` існує,
але **унікального індексу немає і за нею ніхто не дедуплікує**. Подвійний клік, повтор після
таймауту чи ретрай проксі створюють друге повідомлення.

Це рівно той випадок, коли дефект проявляється лише під навантаженням: поки відповідь приходить за
20 мс, ніхто не встигає натиснути двічі; коли через C1 вона йде 3 секунди — встигають усі.

Цільова форма очевидна з наявної схеми: унікальний індекс на `client_id` плюс шлях
«повернути наявне при конфлікті». Важливо, щоб повторний запит повертав **той самий** `id`, а не 409.

### C4. Немає обробки помилок узагалі — **Критично**

У `src/index.ts` немає термінального middleware `(err, req, res, next)`, а в асинхронних обробниках
немає жодного `try/catch`. Наслідки складаються в неприємний ланцюжок:

- відхилений проміс в async-обробнику Express 4 **не** перетворюється на відповідь — запит просто
  зависає, а клієнт чекає (Envoy має `timeout: 0s`, тобто не обірве його ніколи);
- незахоплений rejection у Node 22 за замовчуванням завершує процес;
- `restart: on-failure` тихо піднімає його, ховаючи факт падіння;
- разом із процесом гинуть **усі** WebSocket-зʼєднання інстанса, а клієнт не перепідключається (R3).

Тому один некоректний ввід виглядає для користувача як «realtime іноді просто перестає працювати».

### C5. Пул MySQL: 10 зʼєднань, необмежена черга — **Високо**

`mysql.createPool(config.mysqlUrl)` (`src/db/mysql.ts:4`) без опцій. Перевірено в
`node_modules/mysql2/lib/pool_config.js`: `connectionLimit` за замовчуванням `10`, `queueLimit` — `0`,
що означає чергу **без обмеження**. Немає ні межі, ні таймауту очікування зʼєднання.

Під навантаженням це дає найгіршу форму відмови: замість швидкого «сервер зайнятий» система
накопичує чергу в памʼяті й відповідає дедалі повільніше. У поєднанні з N+1 (D6), де один
`GET /api/conversations` займає до `1 + 2N` зʼєднань поспіль, десятка вичерпується дуже швидко.

### C6. Створення розмови без транзакції — **Середньо**

```js
const [created] = await pool.execute('INSERT INTO conversations (title) VALUES (?)', [title]);
const id = created.insertId;
for (const uid of participantIds) {
  await pool.execute('INSERT INTO conversation_participants ...', [id, Number(uid)]);
}
```

`src/routes/conversations.js:42-49`. Учасники додаються по одному, послідовно, поза транзакцією.
Збій на середині лишає розмову з частиною учасників — вона є в БД, але частина людей її не бачить.
`participantIds` до того ж не обмежений за довжиною й не перевіряється на дублікати та існування
користувачів (D5). Одна вставка з кількома рядками всередині транзакції прибирає і ризик, і N
зайвих обходів мережі.

## 2. Real-time / WebSockets

### R1. Немає heartbeat — витік напівмертвих зʼєднань — **Високо**

```ts
const clients = new Set<Client>();
// ...
ws.on('close', () => clients.delete(ws));
```

`src/ws/hub.ts:6,23`. Видалення відбувається **лише** на `close`. Бібліотека `ws` у переважній
більшості випадків шле `close` і після `error`, тож сам по собі цей рядок не є головною дірою.
Справжня проблема — **відсутність ping/pong**: коли клієнт зникає без TCP FIN (втрата Wi-Fi, sleep
ноутбука, NAT, обрив мобільної мережі), подія `close` не настає ніколи. Envoy з `timeout: 0s` теж
нічого не обриває.

Кожен такий «зомбі» тримає обʼєкт `WebSocket`, його внутрішні буфери й `Set` підписок. Вони
накопичуються монотонно й звільняються лише при перезапуску процесу. Це класичний повільний витік:
на демо непомітний, за тиждень аптайму — суттєвий.

Лікується серверним `ping` з інтервалом і `terminate()` при пропущеному `pong`, плюс дублюючим
прибиранням на `error`.

### R2. Немає контролю backpressure — **Високо**

```ts
if (ws.subs?.has(conversationId) && ws.readyState === WebSocket.OPEN) {
  ws.send(data);
}
```

`src/ws/hub.ts:30-31`. Перевіряється лише `readyState`. Якщо споживач повільний або його TCP-вікно
закрите, `send()` не блокується — він **буферизує дані в памʼяті процесу**, і `bufferedAmount` ніхто
не дивиться. Один зависаючий клієнт в активній розмові тягне купу в гору без будь-якої межі.

Правильна поведінка — перевіряти `ws.bufferedAmount` проти порогу й або пропускати кадри, або
розривати зʼєднання з таким клієнтом: у чаті свіжість важливіша за повноту, а клієнт усе одно може
дочитати історію через HTTP.

Додатковий бік тієї ж проблеми — **вхідний** напрямок: `maxPayload` у `ws` за замовчуванням 100 МБ,
а `m.conversationIds` не обмежений за довжиною (`src/ws/hub.ts:17`), тож один кадр може змусити
сервер створити величезний `Set`. Потрібні і менший `maxPayload`, і межа на кількість підписок.

### R3. Клієнт ніколи не перепідключається — **Високо**

`connectWs()` викликається лише з `loadConversations()`, тобто на завантаженні сторінки й після
створення розмови. Обробників `onclose` та `onerror` немає взагалі (`web/app.js:27-29`). Будь-який
розрив — перезапуск процесу після C4, деплой, перемикання мережі — робить вкладку **назавжди
мертвою**: повідомлення не приходять, і жодного індикатора про це немає. Користувач бачить порожню
розмову й не знає, що звʼязку немає.

Тут же ще два дефекти того самого шляху:

- `connectWs()` робить `if (ws) ws.close()` і одразу відкриває нове зʼєднання, тож у проміжку між
  ними кадри просто губляться;
- підписка формується зі **знімка** `conversations` на момент `onopen`. Розмова, створена кимось
  іншим, не потрапляє в підписку до повного перезавантаження сторінки.

Потрібні: перепідключення з експоненційною затримкою і джитером, повторна підписка після
відновлення, видимий стан звʼязку в UI і дочитування пропущеного через HTTP після реконекту (бо
Redis pub/sub — доставка «вистрелив і забув», і те, що прийшло під час обриву, втрачено назавжди).

### R4. Немає кімнат: розсилка лінійна за всіма зʼєднаннями — **Середньо**

`broadcast()` обходить **увесь** `Set` клієнтів і фільтрує кожного за `subs`. Складність —
`O(усі зʼєднання)` на кожне повідомлення, а не `O(учасники розмови)`. При 10 тисячах зʼєднань і 100
повідомленнях за секунду це мільйон перевірок за секунду на event loop — і це той самий потік, який
уже страждає від C1.

Структура напрошується сама: `Map<conversationId, Set<Client>>`, тобто справжні кімнати. Тоді
розсилка торкається лише реальних отримувачів. Це також передумова для коректного переходу на
Redis pub/sub.

### R5. Підписка не авторизується — **Високо**

```ts
if (m.type === 'subscribe' && Array.isArray(m.conversationIds)) {
  ws.subs = new Set(m.conversationIds.map(Number));
}
```

`src/ws/hub.ts:16-18`. Сервер приймає **будь-які** id від клієнта й ніколи не перевіряє, чи є цей
клієнт учасником розмови. Втім, перевіряти нема кого: зʼєднання взагалі не має ідентичності (SEC2).

Практично це означає, що будь-хто, відкривши WebSocket, може підписатися на всі id підряд і в
реальному часі читати приватні розмови сторонніх людей. Те саме на HTTP-боці:
`GET /api/messages?conversationId=N` теж не перевіряє участь. Це найсерйозніша діра ізоляції в
проєкті, і будь-яка робота над автентифікацією має закривати обидва шляхи одночасно.

Дрібніше з того ж фрагмента: `map(Number)` мовчки перетворює сміття на `NaN` і кладе його в `Set`;
некоректний кадр не отримує жодної відповіді про помилку.

### R6. Стан realtime живе в памʼяті процесу — **Критично для масштабування**

`clients` — це модульний `Set`, тобто стан **одного процесу**. Envoy розподіляє навантаження круговим
методом і **не має session affinity**, тому після `docker compose up -d --scale api=3` HTTP-запит
користувача й його WebSocket майже напевно опиняються на різних інстансах.

Наслідок жорсткіший, ніж «частина повідомлень не доходить». Фронтенд рендерить **власне** щойно
надіслане повідомлення виключно з відлуння по WebSocket (`web/app.js`, відповідь на `POST` явно
ігнорується). Тож коли запис пішов на інстанс A, а сокет автора висить на інстансі B, автор
**не бачить власного повідомлення**. Воно збережене, але екран порожній — виглядає як повна втрата.

Redis 7 уже піднятий у `docker-compose.yml`, його URL є в `config.redisUrl`, але клієнтська
бібліотека не встановлена й ніщо його не використовує. Це і є передбачене місце для fan-out через
pub/sub.

## 3. Data Integrity & Types

### D1. `createdAt` розходиться між сховищами — **Високо**

```ts
const createdAt = new Date();          // час процесу застосунку
await mongo().collection('message_bodies').insertOne({ ..., createdAt });
return { id, conversationId, senderId, body, createdAt };
```

`src/services/messages.ts:25-35`. У MySQL колонка має `DEFAULT CURRENT_TIMESTAMP`, тобто час
**сервера БД**. У Mongo пишеться `new Date()`, тобто час **процесу Node**. Це два різні джерела часу,
між якими є і затримка, і потенційний дрейф годинників між контейнерами.

Гірше те, що одне й те саме повідомлення показує **різний час залежно від шляху доставки**:
`GET /api/messages` віддає `created_at` з MySQL, а кадр WebSocket несе `createdAt` з памʼяті процесу.
Тобто час повідомлення змінюється після перезавантаження сторінки.

Супутнє: `TIMESTAMP` без дробової частини має точність до секунди, тож усі повідомлення в межах
однієї секунди мають однаковий час і за ним неможливо стабільно сортувати. Сортування має йти за
`id` (як зараз і зроблено), а `created_at` лишатися суто відображенням — це варто зафіксувати явно.

Рішення: одне джерело істини. Проставляти час у застосунку і писати те саме значення в обидва
сховища явним параметром, або брати час БД і копіювати його в Mongo.

### D2. Немає індексу на `messages.conversation_id` — **Високо**

У таблиці `messages` єдиний індекс — первинний ключ. При цьому **кожен** запит до повідомлень
фільтрує саме за `conversation_id`: історія розмови, `COUNT(*)`, `ORDER BY id DESC LIMIT 1` для
останнього повідомлення. Усе це — повні сканування таблиці, які деградують лінійно з ростом даних і
множаться на N через N+1 (D6).

```bash
docker compose exec mysql mysql -uroot -proot relay -e "SHOW INDEX FROM messages"
docker compose exec mysql mysql -uroot -proot relay -e "EXPLAIN SELECT * FROM messages WHERE conversation_id = 1"
```

Складений індекс `(conversation_id, id)` покриває всі три шаблони, включно з keyset-пагінацією (D7).

### D3. Валідація на межі майже відсутня — **Високо**

```js
const { conversationId, senderId, body, clientId } = req.body || {};
if (!conversationId || !senderId || !body) {
  return res.status(400).json({ error: 'conversationId, senderId and body are required' });
}
```

`src/routes/messages.js:10-13`. Тут кілька окремих дефектів:

- **Перевірка на істинність замість перевірки типу.** Рядок `"12abc"` проходить перевірку, далі
  `Number("12abc")` дає `NaN`, і це `NaN` іде прямо в параметр SQL-запиту. Жодного захисту між ними
  немає, а помилка драйвера стане незахопленим rejection (C4). Показово, що `GET` у тому ж файлі
  робить `Number()` **до** перевірки й тому `NaN` відсікає — тобто два обробники поруч валідують
  по-різному.
- **`body` не має верхньої межі.** Клієнт може надіслати мегабайти: вони підуть у `pbkdf2Sync` (де
  час зростає з розміром входу) і повністю осядуть у Mongo. Немає ні межі довжини, ні `trim`.
- **`participantIds` не обмежений** ні довжиною, ні перевіркою існування користувачів
  (`src/routes/conversations.js:38-40`).
- **Немає перевірки існування розмови й участі відправника.** Можна писати в неіснуючий
  `conversationId` — рядок створиться, бо зовнішніх ключів немає (D5).

Валідацію треба робити один раз на межі, з приведенням типів до будь-якого I/O, і виносити в
спільний хелпер, а не дублювати по-різному в кожному обробнику.

### D4. Роути нетипізовані — **Середньо**

`tsconfig.json` має `allowJs: true` і `checkJs: false`, а всі три роути — `.js`. Тобто
`src/routes/conversations.js`, `messages.js` і `search.js` **взагалі не перевіряються** тайпчекером,
хоч і використовують TS-специфічні шляхи імпорту (`from '../db/mysql.ts'`). Рядки з БД там — неявний
`any`, тож помилка в назві поля виявиться лише в рантаймі.

Це особливо контрастує з `strict: true` для решти коду. До того ж `noEmit: true` і запуск через
`tsx` означають, що типи ніде не перевіряються автоматично — немає ні кроку збірки, ні CI.

Супутнє в тому ж шарі: `_id: id as never` (`src/services/messages.ts:27`) — приведення, яке
відключає перевірку замість того, щоб описати тип документа Mongo. І `insertId` типізовано як
`number`, тоді як `messages.id` у схемі — `BIGINT`; за межами 2^53 це розійдеться.

### D5. Модель даних без обмежень — **Середньо**

- **Немає жодного зовнішнього ключа.** Повідомлення може посилатися на неіснуючу розмову чи
  користувача, учасник — на видаленого користувача. Цілісність не забезпечує ніхто: ні БД, ні код.
- **Немає унікальності на `client_id`** (див. C3) і на `users.email`.
- **Неузгоджені типи ключів:** `conversations.id` і `users.id` — `INT`, `messages.id` — `BIGINT`,
  `messages.conversation_id` — `INT`.
- **Немає позиції прочитання.** Індикатор непрочитаного живе лише в памʼяті вкладки, скидається при
  перезавантаженні й не узгоджений між пристроями. Для серверного підрахунку потрібна колонка на
  кшталт `conversation_participants.last_read_message_id`.
- **У Mongo немає індексів** на `conversationId` чи `body`, тож майбутній пошук (`tasks/search.md`)
  за замовчуванням буде повним скануванням колекції.

### D6. N+1 у списку розмов — **Високо**

`src/routes/conversations.js:20-31` у циклі по розмовах виконує два окремі запити на кожну:
останнє повідомлення й `COUNT(*)`. Разом `1 + 2N` звернень до БД на один HTTP-запит, кожне з яких —
повне сканування через D2, і кожне послідовно займає зʼєднання з пулу на 10 (C5). Згортається в
один запит із `JOIN` і агрегатом.

### D7. Читання історії без пагінації — **Високо**

`GET /api/messages` повертає **всі** повідомлення розмови, а потім робить `$in` по всьому масиву
id у Mongo (`src/routes/messages.js:26-43`). Ні `LIMIT`, ні курсора. Розмова на 100 тисяч
повідомлень намагається матеріалізуватися в памʼяті процесу цілком — і при цьому лишається
відкритою для будь-кого (R5). Потрібна keyset-пагінація за `id` з обмеженням зверху на `limit`.

## 4. Безпека

### SEC1. Збережений XSS через назву розмови — **Високо**

```js
li.innerHTML =
  `<span>${c.title} (${c.messageCount})</span>` + (c.unread ? '<span class="dot">●</span>' : '');
```

`web/app.js:19-20`. `c.title` приходить із БД, а туди — з `prompt()` без будь-якої санітизації, і
вставляється через `innerHTML`. Розмова з назвою `<img src=x onerror=alert(1)>` виконає код у
браузері **кожного**, хто її бачить.

Прикметно, що решта фронтенду зроблена правильно: `appendMessage` використовує `textContent`, а
`renderResults` — `textContent` і `append()`. Тобто це поодинокий недогляд, і виправляється він
переходом на `textContent` у цьому одному місці.

### SEC2. Автентифікації немає взагалі — **Середньо** (для демо) / блокер для продакшену

`web/app.js` хардкодить `const userId = 1`, а сервер беззастережно довіряє `userId` та `senderId` з
запиту. Наслідки: можна писати від імені будь-кого, читати будь-яку розмову по HTTP і по WebSocket
(R5), створювати розмови від чужого імені. Участь у розмові не перевіряється ні на читанні, ні на
записі.

Для навчального стенду це прийнятно, але будь-яка функція, що припускає чесність клієнта, має це
явно зазначати. Rate limiting (`tasks/rate-limiting.md`) — приклад: ліміт «на користувача» без
автентифікації обходиться підстановкою іншого `senderId`.

Дрібніше: `.env` із `root/root` присутній у робочій копії (в `.gitignore` він є, тож у git не
потрапляє), MySQL і Mongo публікують порти на хост без пароля для Mongo.

## 5. Структурні прогалини

### S1. Сід-скрипт стирає всі тіла повідомлень — **Критично** (не перевірено)

```ts
const bodies = mongo().collection('message_bodies');
await bodies.deleteMany({});
await bodies.insertMany([ /* 3 демо-повідомлення */ ]);
```

`docker/db/seed.ts:4-10`. Тут асиметрія між двома сховищами: MySQL виконує `docker/db/mysql.sql`
**лише** коли каталог даних порожній, а сервіс `seed` — це одноразовий контейнер, який запускається
при кожному `docker compose up` (бо `api` залежить від його успішного завершення).

Отже при звичайному перезапуску стеку **без** `-v`: рядки в MySQL зберігаються всі, а колекція тіл
у Mongo обнуляється й наповнюється трьома демо-записами. Усі раніше написані повідомлення
перетворюються на порожні бульбашки через `?? ''` (C2) — тихо, без жодної помилки.

Це варто перевірити першим, бо якщо підтвердиться, то псує дані при кожному буденному
`docker compose restart`-циклі:

```bash
docker compose up -d
# надіслати кілька повідомлень через UI
docker compose down && docker compose up -d
# порівняти:
docker compose exec mysql mysql -uroot -proot relay -N -e "SELECT COUNT(*) FROM messages"
docker compose exec mongo mongosh relay --quiet --eval 'db.message_bodies.countDocuments()'
```

Виправлення: зробити сід ідемпотентним (`updateOne` з `upsert` замість `deleteMany` + `insertMany`)
або запускати його лише коли колекція порожня.

### S2. Немає graceful shutdown — **Середньо**

`src/index.ts` не обробляє `SIGTERM`/`SIGINT`. При `docker compose restart` процес помирає миттєво:
запити в польоті обриваються (зокрема між двома половинами подвійного запису — прямо в вікно C2),
зʼєднання з MySQL і Mongo не закриваються, WebSocket-клієнти не отримують коду закриття. Потрібні
`server.close()`, відмова від нових зʼєднань, дочікування активних запитів із таймаутом і закриття
пулів.

### S3. Немає інструментів контролю якості — **Середньо**

- **Тестів немає взагалі**, як і тестового раннера. Для стека такого типу найцінніші — інтеграційні
  тести проти піднятого `docker compose` (саме там живуть цікаві дефекти), плюс юніти на чисту
  логіку. Робити це можна вбудованим раннером Node через `tsx`, без нової залежності.
- **Немає лінтера й форматера**, немає CI. У поєднанні з `noEmit` і `checkJs: false` це означає, що
  **ніщо** не перевіряє код автоматично — навіть типи.
- **Логування — це `console.log` в одному місці.** Немає ні структурованих логів, ні кореляційних
  id, ні метрик, ні healthcheck для сервісу `api` (у MySQL він є, у застосунку — ні). Через це
  падіння з C4 непомітне: `restart: on-failure` ховає його, і єдиний слід — розірвані сокети.
- **`restart: on-failure` маскує збої.** На час діагностики його варто прибрати, щоб падіння було
  видно.
- **Envoy має `timeout: 0s`**, тобто жоден запит ніколи не буде обірваний за таймаутом. Заблокований
  запит висітиме вічно, займаючи ресурси з обох боків. Кінцевий таймаут потрібен.
- **`GET /api/search` — заглушка**, що завжди повертає `[]` (`src/routes/search.js`); це очікувано,
  бо це одне з завдань у `tasks/`.
- **Порожні `docs/` і `spec/`** — до цього аудиту в репозиторії не було жодного письмового сліду
  міркувань, хоча README прямо просить лишати їх у репозиторії.

## 6. Пропонований порядок робіт

Порядок визначається двома критеріями: спершу те, що **псує або втрачає дані**, потім те, що робить
подальшу діагностику можливою, і аж потім оптимізації.

1. **S1** — перевірити гіпотезу про стирання тіл сідом. Якщо підтвердиться, це найдорожчий дефект:
   він знищує дані під час буденного перезапуску.
2. **C4** — додати error middleware і `try/catch`. Поки процес падає від будь-якої помилки драйвера,
   решту вимірювань неможливо довіряти, а падіння ще й ламає realtime.
3. **C1** — прибрати `pbkdf2Sync` (найімовірніше — разом із полем `signature`, бо його ніхто не
   читає). Це знімає домінуючу причину деградації під навантаженням.
4. **D2 + D6 + D7** — індекс `(conversation_id, id)`, згортання N+1 в один запит, пагінація. Одна
   зв'язана група: усі три стосуються того самого шляху читання.
5. **C3** — унікальний індекс на `client_id` і повернення наявного при конфлікті. Робити **після**
   C1, бо повільні відповіді — головне джерело повторних надсилань.
6. **R6 + R4** — кімнати як структура даних, потім fan-out через Redis pub/sub. Це знімає найгірший
   симптом: «я не бачу власного повідомлення» при кількох інстансах.
7. **R3 + R1 + R2** — перепідключення на клієнті, heartbeat і backpressure на сервері. Разом роблять
   realtime придатним для тривалої роботи.
8. **D3 + D1** — валідація на межі та єдине джерело часу.
9. **SEC1** — `textContent` замість `innerHTML` (виправлення на один рядок, варте окремого коміту).
10. **C2** — свідоме рішення щодо подвійного запису й узгодженості; потребує окремого запису рішення
    в `docs/`, бо тут немає безкоштовного варіанту.
11. **S2 + S3** — graceful shutdown, тести, лінтер, логування, таймаут Envoy.

**C5** (розмір пулу) свідомо не в топі: доки event loop блокується на C1, пул не є вузьким місцем.
Його варто налаштовувати вже після C1 і за результатами вимірювання.
